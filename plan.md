## ЛР1. Добыча корпуса документов

**Что сделано.** Два корпуса на тему туризма.
- Первый — 30 000 английских статей через MediaWiki API: 15 000 из Wikivoyage (первые по алфавиту) и 15 000 из Wikipedia (обход в ширину от `Category:Tourism`, глубина 3). На нём сделана ЛР4.
- Основной — **1 000 000 документов** четырёх источников из дампов и архивов (`scripts/download_million.py`, каталог `data_1m/`):
  - Wikipedia — 620 164 статьи из дампа `enwiki` (25 ГиБ), отобранные по «туристичности»;
  - Reddit — 296 250 постов r/travel, r/solotravel, r/backpacking от 100 слов, архив Arctic Shift;
  - Travel Stack Exchange — 48 768 вопросов с ответами, дамп с archive.org;
  - Wikivoyage — все 34 818 статей из дампа.

**Как работает.**
- Первый корпус: `scripts/download.py` ходит в MediaWiki API (`list=allpages` / `list=categorymembers`, метаданные пачками по 50). HTML берётся через `action=render` (1–3 с на статью; `action=parse` давал 10–20 с), 4 потока, keep-alive и gzip. Частота запросов к API ограничена (подробности — в отчёте).
- Миллион: через API качался бы ~3,5 суток, поэтому дампы. Дамп качается частями по 64 МиБ в 2 соединения с докачкой.
- Отбор Wikipedia: явно туристических статей всего ~300 тыс., поэтому тема «туризм + места». Оценка статьи = туристические слова (до 20) + 3 за признак места (`{{coord}}` или инфобокс места) + 5 за туристическую категорию. Берутся лучшие из 1,5 млн кандидатов от 100 слов. Разбор дампа — 16 процессов, 59 + 13 мин.
- Reddit добавлен, чтобы Wikipedia не была 92 % корпуса (стала 62 %). Travel SE — потому что страницы сайта отдают роботу 403, а Common Crawl отсюда слишком медленный.
- Сырьё: первый корпус — HTML (`data/raw/<источник>/*.html`); миллион — вики-разметка `.wiki` (Wikipedia, Wikivoyage) и собранный HTML `.html` (Travel SE, Reddit). Плюс `meta.jsonl`: id, заголовок, URL, категории или метки, число слов.
- Текст: из HTML — `scripts/extract.py` (`html.parser`, выкидываются теги, скрипты, сноски, навигация); из вики-разметки — свой разбор регулярными выражениями: шаблоны, таблицы, сноски вырезаются, ссылки становятся текстом, хвостовые разделы (References и т. п.) отрезаются, у листингов Wikivoyage остаются название, описание, адрес, цена.
- `scripts/stats.py [каталог таблица]` — статистика. Поисковики: встроенный поиск MediaWiki, поиск Travel SE и Reddit, Google с `site:`; примеры запросов и недостатки выдачи — в отчёте.

**Главные цифры.** Миллион: сырьё — 13,9 ГиБ (вики-разметка и HTML), текст — 5,6 ГиБ, 972 млн слов, медиана 457 слов на документ (Wikipedia 749, Reddit 163); Wikipedia — 62 % документов и 87 % слов; дампы — 26 ГиБ. Порог отбора Wikipedia — оценка 3; по выборке 30 % отобранных статей не содержат туристических слов, есть и посторонние (певица, датчик угла поворота) — это главный недостаток. Первый корпус: сырой HTML — 2,8 ГиБ, текст — 210 МиБ.

## ЛР2. Поисковый робот

**Что сделано.** `crawler.py` на Python (стандартная библиотека, PyYAML, драйвер `pymongo`). Единственный аргумент — yaml-конфиг с секциями `db` (адрес набора реплик MongoDB и имя базы), `logic` (задержка, период переобкачки, таймаут, User-Agent) и `sources` (стартовые URL, правила обхода, лимит). База — **распределённая: MongoDB, набор реплик из трёх узлов** в Docker.

**Как работает.**
- Обход в ширину по ссылкам; у каждого источника свой поток и своя задержка между запросами.
- Стартовые страницы: Wikivoyage — от `/wiki/Destinations`, Wikipedia — от `Category:Tourism` по подкатегориям, глубина до 4.
- Ссылки берутся только из `#mw-content-text`, иначе блок категорий уводил бы обход вверх по дереву.
- URL нормализуются: относительные ссылки, регистр, порт, якорь, кодировка пути, порядок параметров. Перенаправления MediaWiki сохраняются под каноническим URL (`<link rel="canonical">`), повторы помечаются как дубли.
- `robots.txt` соблюдается. Скачивать его приходится самим: на User-Agent `Python-urllib` Wikimedia отвечает 403.
- **База**: MongoDB 7.0, набор реплик `rs0` — `docker-compose.yml`, три контейнера на портах 27017–27019.
  - Один узел основной (принимает запись), два вторичных хранят полные копии.
  - Если основной узел падает, оставшиеся за ~10 с выбирают новый, и драйвер сам на него переключается.
  - Запись подтверждается большинством узлов (`w=majority`), поэтому отказ одного узла её не теряет.
  - Коллекции: `documents` (ключ — url; source, html, fetched_at в Unix time, Last-Modified, хеш) и очередь `frontier` (ключ — url; source, depth, status new/done/dup/error, seq — порядок постановки в очередь).
  - Каждая страница вместе с новыми ссылками записывается одной многодокументной транзакцией; такие транзакции доступны именно в наборе реплик.
- **Остановка в любой момент**: Ctrl+C, SIGTERM, даже `kill -9`. Незавершённая транзакция откатывается, повторный запуск продолжает со следующего необработанного URL.
- **Переобкачка**: документ старше `recrawl_after` проверяется условным GET с `If-Modified-Since`. Ответ 304 — не изменился, 200 — страница перезаписывается.
- Пробный прогон — 1000 + 1000 документов (500 МиБ HTML), около 2,2 с на запрос к источнику. Прогон делался ещё с SQLite, данные перенесены в MongoDB (`scripts/migrate_sqlite.py`), статистика совпала. На каждом узле база занимает около 146 МиБ: MongoDB сжимает данные.
- Демонстрация отказа (`scripts/failover_demo.py`): основной узел остановлен посреди работы робота, через 10 с выбран новый, робот продолжил писать без перезапуска; вернувшийся узел догнал остальных.

## ЛР3. Токенизация

**Что сделано.** Токенизатор на C++: функция `tok::tokenize` в `src/tokenizer.h` (её же подключают индексатор и поиск) и утилита `build/tokenizer`.

**Как работает.**
- Текст декодируется из UTF-8 за один проход. Токен — непрерывная последовательность букв и цифр Юникода, остальное — разделители. Класс символа определяет `iswalnum` в локали `C.UTF-8`.
- Регистр понижается `towlower`; для ASCII всё делается сравнениями, без вызовов библиотеки. Некорректный UTF-8 считается разделителем.
- Режим `-s` принимает список файлов и считает статистику, отдельно время чтения и время токенизации.
- Достоинства: просто, быстро, работает для любого языка с пробелами.
- Недостатки (13 примеров в отчёте):
  - `Lviv's` → `lviv`, `s`;
  - `3,000` → `3`, `000`;
  - `U.S.` → `u`, `s`;
  - `café` и `cafe` — разные токены;
  - тайский текст и хинди рвутся на диакритических знаках;
  - склеенные ячейки инфобоксов в первом корпусе (`coordinates49`); в миллионе их нет — инфобоксы вырезаются из вики-разметки.

**Главные цифры.** 995 млн токенов, средняя длина — 4,83 символа (Wikipedia 4,90, Reddit 4,16). Собственно токенизация линейна, ~5 мкс на КиБ. Весь корпус (5,6 ГиБ) — 165 с, из них 129 с — чтение миллиона мелких файлов; склеенный в один файл корпус обрабатывается за 37 с.

## ЛР4. Стемминг

**Что сделано.** В поисковую систему ЛР7–8 добавлен поиск без учёта словоформ — стеммер Портера (1980). Написан самостоятельно по статье, `src/porter.h`; лемматизация не делалась.

**Как работает.**
- Слово рассматривается как чередование согласных и гласных. Суффиксы снимаются за 5 шагов по правилам с условием на «меру» основы: `generalization` → `generalize` → `general` → `gener`, `hiking` → `hike`, `ponies` → `poni`.
- Стеммируются только слова из латинских букв длиннее 2 символов.
- Стемминг стоит в индексе и в запросе. Индексатор ЛР7 с ключом `-s` пишет основы и ставит бит 0 в поле `flags` заголовка индекса — это поле в ЛР7 и оставлялось для расширений.
- Поиск ЛР8 видит флаг и сам приводит слова запроса к основам. Разбор запроса не меняется.
- Оценка качества:
  - 14 запросов: 10 на словоформы (`cheap hostels`, `skiing resorts`…) и 4, где Портер склеивает разное: `news` → `new`, `organ` и `organization`, `general`, `university`;
  - мера — P@10 (выдача булева поиска — по номеру документа);
  - пул — 225 документов, оценки 0/1 ставились вслепую (не видно, какая система нашла документ), с обоснованием каждой в `data/qrels.tsv`. **Оценки ставили ИИ-оценщики (субагенты Claude)** — перед сдачей их стоит просмотреть.
- Причины ухудшений:
  - склейка разных слов: `news` → `new`, а `new` встречается в 29 раз чаще;
  - основа шире формы из запроса: `springs` → `spring`, то есть весна;
  - выдача по номеру документа: новые документы, где тема лишь упомянута, вытесняют релевантные.
- Улучшение — бонус за точное совпадение: сначала документы с точными формами, затем найденные по основе. По расчёту P@10 = 0,49 при полноте стемминга; в поиске это не реализовано.

**Главные цифры.**

| | Без стемминга | Со стеммингом |
|---|---|---|
| Термов в словаре | 775 205 | 713 920 (−8%) |
| Средняя P@10 | 0,48 | 0,41 (лучше по 5 запросам, хуже по 8) |
| Найдено документов | — | в 1,6–9,7 раза больше |
| Оценка числа найденных релевантных | 2 279 | 4 101 (+80%) |

**Демонстрация.**

## ЛР5. Закон Ципфа

**Что сделано.** Частотный список терминов корпуса и график «частота от ранга» в логарифмической шкале с наложенным законом Ципфа. Необязательная часть (Мандельброт) не делалась.

**Как работает.**
- `scripts/zipf.py` пропускает все тексты через один процесс токенизатора ЛР3 (между файлами — перевод строки) и считает частоты (`collections.Counter`). Затем сортирует термины по убыванию частоты, равные — по алфавиту; ранг — позиция в списке.
- Закон Ципфа: f = C/r, C = f(1) = 70 066 836 (частота `the`).
- matplotlib на машине нет, поэтому график рисуется пакетом `pgfplots` прямо в отчёте по 430 точкам: ранги прорежены через 3% по логарифмической шкале.
- Причины расхождения:
  - **начало** (ранги до 70): закон почти выполняется (до 1,25 раза), но частоты служебных слов задаёт грамматика: `of` ≈ `and`;
  - **середина** (70–10 417): частоты выше закона до 1,7 раза — тематические слова (`city` 45-я, `museum` 177-я), смесь источников (`i` 20-я, `you` 58-я — из постов Reddit), числа, осколки токенизации (`s`, `t`);

- На корпусе 30 тыс. хвост отклонялся всего до 6 раз: C растёт вместе с числом токенов (×33), а словарь — по Хипсу медленнее (×5).

## ЛР7. Булев индекс

**Что сделано.** Индексатор на C++ без STL: свой динамический массив, хеш-таблица, сортировка. STL есть только в токенизаторе ЛР3, где правила курса её разрешают. Индекс — один бинарный файл собственного формата `BIDX`, формат описан в отчёте побайтово.

**Как работает.**
- `scripts/doclist.py` делает `data/docs.tsv`: путь, заголовок, URL. Номер строки — docID: Wikivoyage — 0–34 817, Wikipedia — 34 818–654 981, Travel SE — 654 982–703 749, Reddit — 703 750–999 999. Источники скрипт находит сам.
- Индексатор читает документы по порядку и токенизирует. Каждый токен ищется в хеш-таблице (открытая адресация, FNV-1a, удвоение при заполнении на 50%), и docID дописывается в список терма, если его там ещё нет.
- Списки документов получаются отсортированными сами, потому что документы идут по возрастанию номера. Сортируется только словарь — слиянием (merge sort) по байтам строки, 1,9 с.
- Формат файла: заголовок 64 байта (сигнатура `BIDX`, версия, размер заголовка, флаги, число документов N, термов T и записей P, размеры записей, смещения разделов) → таблица документов (прямой индекс: заголовок, URL, число токенов) → таблица термов (отсортирована, записи по 16 байт, поэтому возможен двоичный поиск) → списки docID → пул строк.
- Формат расширяемый: номер версии, размеры заголовка и записей, флаги, смещения разделов. Флаги «стемминг» (ЛР4) и «списки сжаты» (ЛР11) добавлены потом.
- Юнит-тесты на C++ разбирают файл индекса собственным читателем, написанным по описанию формата, — так проверяется и индексатор, и само описание.
- Средняя длина терма (8,03) больше средней длины токена (4,83): частые слова короткие, а словарь в основном из редких.

**Главные цифры.** 1 000 000 документов, 3 974 421 терм, 364 млн записей, файл 1,6 ГиБ (88 % — списки документов). Индексация — 148 с (0,15 мс на документ, 25 мкс на КиБ): половина — чтение миллиона файлов, половина — словарь; память — 2,1 ГиБ. Время прогона скачет 150–280 с в зависимости от кэша ОС. По закону Хипса β ≈ 0,64. Уже при росте в 10 раз списки займут 14–28 ГиБ памяти — нужна индексация блоками со слиянием (SPIMI); при росте в 1000 раз индекс (~1,5 ТБ) не поместится на диск одной машины.

## ЛР8. Булев поиск

**Что сделано.** Поиск на C++ без STL над индексом ЛР7: утилита командной строки `build/search` и веб-сервис `web/server.py` из двух страниц — форма и выдача по 50 результатов со ссылками «Предыдущие/Следующие 50».

**Как работает.**
- Синтаксис: пробел, `&&` или `&` — И; `||` или `|` — ИЛИ; `!` — НЕ; скобки. Приоритет: НЕ > И > ИЛИ.
- Слово запроса делится тем же токенизатором, что и документы, поэтому регистр не важен, а `Hewlett-Packard` превращается в `hewlett && packard`.
- Парсер — рекурсивный спуск, прощает ошибки ввода: любые пробелы, одиночные `&` и `|`, незакрытую или лишнюю скобку, висящий оператор, `!!`. Разобранный запрос печатается (`parsed:`), чтобы было видно, как он понят.
- Выполнение идёт над отсортированными списками docID слиянием двумя указателями:
  - И — пересечение начиная с самого короткого списка;
  - `a && !b` — разность, без построения дополнения;
  - ИЛИ — объединение;
  - одиночное НЕ — дополнение до всех документов.
- Выдача — по номеру документа, без ранжирования.
- Веб-сервис — Python `http.server`. Он держит один процесс `search` в режиме `-p` (строки «смещение, лимит, запрос»), чтобы не грузить индекс на каждый запрос, и экранирует HTML.
- Корректность проверена так:
  - 300 случайных запросов сверены с вычислением на множествах (`std::set`) в юнит-тестах на C++;
  - 35 тождеств на индексе корпуса (де Морган, включения–исключения, `N(a) + N(!a) = 1000000`);
  - число документов по одному терму совпадает с df из ЛР7.

**Главные цифры.** Индекс 1,6 ГиБ загружается 0,9 с. Запрос — медиана 0,61 мс, среднее 2,6 мс (на 30 тыс. было 91 мкс — растёт с длиной списков). Самый долгий — ИЛИ из 20 частых слов, 23,5 мс: накопленный результат заново сливается с каждым следующим списком. Выдача по docID, поэтому статья Wikipedia «Lviv» — только 101-я по запросу `lviv`.

**Демонстрация.**

```sh

python3 tests/test_web.py              # тест веб-сервиса (он на Python)

  | build/search ../lab7/data/index.bin -n 3
python3 web/server.py --port 8080      # открыть http://127.0.0.1:8080/
                                       # запрос: (castle || palace) germany !museum, затем «Следующие 50»; Ctrl+C — стоп
```

## ЛР11. Сжатие

**Что сделано.** Списки документов (координатные блоки) булева индекса ЛР7 сжаты кодом Variable Byte по разностям docID. Индекс на 1 млн документов: 1 584 → 615 МиБ. Поиск ЛР8 работает по сжатому индексу без изменений в логике запросов.

**Как работает.**
- Вместо docID хранятся разности соседних номеров: `824, 829, 215406` → `824, 5, 214577`.
- Разность — кодом VByte (`lab11/src/vbyte.h`): группы по 7 бит начиная с младших, по байту на группу; старший бит байта = 1 только в последнем байте числа. `824` → `38 86`, `5` → `85`, `214577` → `31 0c 8d`: 6 байт вместо 12.
- Почему VByte: выровнен по байтам — распаковка без работы с отдельными битами, самый простой и быстрый код из лекции; 73 % записей — у частых термов с разностями < 128, там 1 байт вместо 4.
- Формат: индексатор ЛР7 с ключом `-c` ставит бит 1 (значение 2) в `flags`; поле `first` записи терма — смещение списка в байтах, длина списка — до `first` следующего терма. Остальное как в ЛР7.
- Чтение: `Index::read_list` распаковывает список в массив docID; через него читают поиск ЛР8 и `lookup`. Пересечение/объединение/разность не менялись.
- Корректность: кодек обратим (юнит-тесты на границах длин и 10⁶ случайных чисел), индекс тот же (`listbench -v`: все 364 млн записей совпали с индексом ЛР7), выдача та же (24 запроса ЛР8, полная выдача 6,2 млн строк — SHA-256 совпал; 500 случайных запросов в тестах).
- Слабые места: VByte не меньше 8 бит на запись (у частых термов гамма-код или битовая карта сжали бы сильнее); распаковка в 1,7–4,2 раза медленнее чтения u32; список распаковывается целиком (лечится прыжками по индексу, ЛР12); память индексации не уменьшилась — сжатие только при записи.

## ЛР13. Ранжирование TF-IDF

**Что сделано.** Ранжированный поиск по схеме TF-IDF lnc.ltc (из лекции). Запрос из одних слов — нечёткий: найдены документы хотя бы с одним словом, порядок по TF-IDF. Запрос с операторами `&& || ! ( )` — строгий булев (как ЛР8), но порядок по TF-IDF. Работает и в утилите `search`, и в веб-сервисе ЛР8, оценка видна в выдаче.

**Как работает.**
- Веса: документ — `1 + log10 tf`, нормировка на длину вектора документа (lnc); запрос — `(1 + log10 tf) · log10(N / df)`, нормировка (ltc); оценка — косинус = скалярное произведение. Пример лекции «best car insurance» → 0,80 (юнит-тест 1).
- Почему нормировка: статья Wikipedia в 6 раз длиннее поста Reddit; без неё длинные статьи всегда были бы выше.
- Формат: индексатор ЛР7 с ключом `-t` ставит флаг 4. Запись списка — пара (docID, tf): без сжатия 8 байт, со сжатием — VByte(разность) VByte(tf). Запись документа 16 байт: добавлена длина вектора `norm` (float). Флаги независимы: `-c -t` → 6, со стеммингом → 7.
- Частота считается при вставке токена в словарь (терм уже был в текущем документе → +1 к последней записи); длины векторов — одним проходом по спискам после всех документов.
- Поиск (`lab13/src/rank.h`, без STL): накопители оценок на N документов; по каждому слову запроса (не под НЕ) распаковывается список с частотами и прибавляется вклад; нечёткий — результат все затронутые документы; булев — множество ЛР8 с оценками из накопителей; сортировка слиянием по убыванию оценки, при равенстве по docID.
- Оценка качества: 12 запросов с потребностями, три системы — булев ЛР8 (по docID), TF-IDF нечёткий, TF-IDF со строгим И. Пул — первые 10 каждой, 282 документа. **Оценки 0/1/2 ставили вслепую три субагента Claude** (каждый по 4 запросам, с обоснованием в `data/qrels.tsv`) — перед сдачей их стоит просмотреть.
- Неудачи и причины: длинные документы проигрывают коротким постам (нормировка): статья «Moscow Aviation Institute» 153-я (нечёткий) и 25-я (строгое И), путеводители Wikivoyage по снорклингу в Таиланде — 17–31-е (единственный запрос, где ранжирование хуже порядка по docID). Нечёткий `lviv old town` поднимает документы только с редким `lviv`. Исправление — pivoted normalization или BM25, зоны (заголовки), бонус за все слова.

**Главные цифры.**

| | Булев ЛР8 (по docID) | TF-IDF нечёткий | TF-IDF строгое И |
|---|---|---|---|
| P@10 | 0,20 | 0,50 | 0,68 |
| NDCG@10 | 0,16 | 0,50 | 0,73 (лучше в 11 из 12) |
| Запрос, медиана | 0,26 мс | 15 мс | 3,6 мс |

Индекс с частотами и сжатием — 966 МиБ (ЛР7 — 1 584, ЛР11 — 615), индексация — 173 с, память — 4,0 ГиБ (без частот — 2,1). Ранжирование медленнее в 10–90 раз: распаковка полных списков, включая служебные слова, и сортировка всех найденных.
